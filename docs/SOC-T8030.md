# SoC target: Apple T8030 (A13 Bionic)

The `ios-rust` workspace implements **one** machine:

| | |
|---|---|
| SoC | **Apple T8030 (A13 Bionic)** |
| Device | D79AP-class (iPhone 11); ADT from the IPSW overrides everything |
| Machine name | `apple-t8030` (`ios-rust run -M apple-t8030`) |
| CPU name | `apple-a13` |
| Cores | 2× **Lightning** (performance) + 4× **Thunder** (efficiency) |
| ISA | AArch64 only (no AArch32 at any EL), ARMv8.4-A baseline |
| Apple extensions | GXF (Guarded Execution Facility — GENTER/GEXIT, ported from Inferno `a13_gxf.c`), Apple MMU (16K pages, WXN), AMXv1 (userspace), PAC |
| DRAM | 4 GiB @ `0x800000000` |
| SRAM | `0x19C000000`, SROM `0x100000000`, SEPROM `0x240000000`, AMCC `0x200000000` (all from Inferno `t8030.c` defines) |
| Console | S3C UART0 @ `0x235200000` (UTXH at `+0x20`) |
| Display | DisplayPipe v4 (ADP) @ ADT `reg`; 2436×1125 panel; MIPI-DSI host is the faithful upstream stub |

## CPU instruction set coverage

`crates/a13-cpu/src/isa.rs` enumerates the ARMv8.4-A feature set the A13
implements (LSE atomics, RDM, FCMA, JSCVT, FP16, DOTPROD, SHA3, SM3/SM4,
FJCVTZS, PAC, GXF...). The interpreter executes a verified subset — the
`decode` crate has hand-checked encodings against ARM DDI 0487 with 19
unit tests, and `ios-rust boot` proves the stack end-to-end (interpreter →
bus → UART MMIO → serial + framebuffer).

Honest status lives in `PARITY.md` / `parity.json`:
* decoder + interpreter subset: boots-early-code class coverage
* HVF/KVM accel backends: compiled skeletons (native-speed path for real
  A13 code; the "replace the QEMU binary" speed tier)
* unknown instruction → hard stop with `UnknownInsn{pc,insn}` (never
  silently skipped — Inferno honesty rules)

## One IPSW flow

```
ipsw (file or research-S3 vault key)
  → BuildManifest verify → IM4P unwrap → LZFSE (vendored Apple C)
  → kernelcache fileset load (macho) → ADT-driven device attach
  → a13 interpreter/accel run → UART console + framebuffer (GUI BMP / window)
  → homescreen ladder gates G1✅ G2 G3 G4 (honest verdicts → vault)
```

The device placement is **ADT-driven**: `attach_from_adt` walks the IPSW's
own devicetree `/arm-io` children and instantiates the matching Rust
device model at the real MMIO base — the hardware map comes from the
IPSW itself, exactly like real hardware, XNU, and Inferno.
